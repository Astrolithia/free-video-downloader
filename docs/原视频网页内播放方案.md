# 原视频网页内播放方案

> 产出日期：2026-04-10
> 适用项目：FreeVidGrab / 万能视频下载器

## 1. 目标

在现有“解析视频 + 下载视频 + 视频总结 + 字幕获取”能力之上，新增一条**网页内播放用户粘贴视频链接的原视频**能力。

这里的“原视频”指：

- 不要求用户先下载到本地
- 用户在页面中即可播放
- 播放内容对应用户刚刚粘贴并解析的那条视频
- 播放流程尽量兼容 B 站、YouTube 等 yt-dlp 已支持的平台

本方案只讨论**公开可访问、非 DRM、非会员专属、非登录必需**的视频。

---

## 2. 现状分析

### 2.1 已有能力

当前项目已经具备以下基础：

1. `POST /api/parse` 可解析视频信息和格式列表
2. `GET /api/stream` 可代理单路视频流，并支持 `Range`
3. `GET /api/play/{task_id}` 可播放下载完成后的本地文件
4. 前端已有播放器组件 `VideoPlayer.vue`
5. 当前页面已具备“封面区域切播放器”的交互基础

### 2.2 当前瓶颈

当前要新增“原视频播放”，最大的限制不是前端样式，而是**播放源模型过于简单**。

现在后端更像是在提供：

```ts
type CurrentStreamSource = {
  url: string
  headers: Record<string, string>
}
```

但实际可播放源至少有 4 类：

1. `progressive`
   单个 mp4/webm，浏览器可直接播
2. `hls`
   需要 m3u8 + HLS 播放能力
3. `dash`
   需要 mpd + DASH 播放能力
4. `separate_av`
   只有视频直链和音频直链，没有浏览器友好的 manifest

也就是说，**“一个 url 字符串”不足以稳定表示原视频播放源**。

## 3. 开源方案参考

以下项目适合作为设计参考：

### 3.1 播放器

- [Video.js](https://videojs.org/)
  - 成熟的开源 HTML5 播放器
  - 适合标准 MP4/HLS/DASH 统一播放器壳

- [Shaka Player](https://shaka-player-demo.appspot.com/docs/api/tutorial-welcome.html)
  - 官方文档明确支持 DASH/HLS
  - 更适合处理自适应流和多轨

- [ArtPlayer](https://artplayer.org/document/en/start/option.html)
  - 对中文项目友好
  - 自定义 UI 能力强
  - 能和 `hls.js`、`dash.js`、`mpegts.js` 配合

- [xgplayer](https://v2.h5player.bytedance.com/en/gettingStarted/)
  - 国内生态成熟
  - 支持 MP4/HLS/DASH
  - 适合强调产品化播放体验

### 3.2 yt-dlp Web UI 参考

- [yt-dlp-web-ui](https://github.com/marcopiovanello/yt-dlp-web-ui)
- [webui-yt-dlp](https://github.com/neoxnitro/webui-yt-dlp)

这些项目说明“解析 + 格式选择 + Web UI”本身很成熟，但它们更偏向下载管理，不直接解决“复杂平台原视频页内播放”的兼容问题。

## 4. 推荐路线

## 4.1 总体结论

推荐采用：

**后端统一播放源描述 + 前端播放器适配层**

而不是：

**前端直接拿一个 url 塞进 `<video>`**

### 推荐原因

1. 可以显式区分 `progressive`、`hls`、`dash`、`separate_av`
2. 可以保留后端代理和请求头透传，兼容 B 站等平台
3. 未来更容易接字幕切换、时间戳跳转、倍速和记忆播放
4. 能优雅处理“不支持原视频页内播放”的降级提示

---

## 5. 功能范围建议

## 5.1 P0 范围

先做最稳的首版：

1. 用户解析成功后，出现一个独立按钮：`播放原视频`
2. 用户点击后，在封面区域替换成网页播放器
3. 首版只支持：
   - 单文件 progressive 视频
4. 如果当前链接只能拿到“音视频分离直链、但没有 manifest”，则提示：
   - `当前平台暂不支持原视频页内播放，请先下载后播放`

### P0 不做

1. 自动播放
2. 会员/登录/DRM 视频
3. 边下载边播
4. 弹幕
5. 多音轨切换
6. 原视频播放失败后的复杂重试策略

## 5.2 P1 范围

1. 接入 HLS / DASH 播放支持
2. 接入外挂字幕/原字幕显示
3. 接时间戳跳转
4. 倍速、画中画、全屏、播放记忆
5. 原视频播放失败时自动引导用户切到“下载后播放”

---

## 6. 交互方案

## 6.1 推荐用户流程

1. 用户粘贴链接
2. 点击或自动触发解析
3. 页面展示标题、封面、格式信息
4. 页面出现两个动作按钮：
   - `播放原视频`
   - `下载到本地`
5. 用户点击 `播放原视频`
6. 前端请求后端的“播放源描述接口”
7. 成功时：
   - 封面区域替换为播放器
   - 根据资源类型加载对应播放器
8. 失败时：
   - 给出明确中文提示
   - 不影响下载功能

## 6.2 为什么推荐手动点击播放

不建议“解析完成后自动加载播放器”，原因是：

1. 很多平台的真实流地址有时效性，过早请求会浪费有效期
2. 自动预拉流会增加源站请求量
3. 播放失败时，用户感知更差
4. 手动触发更符合“下载器 + 增值播放”的产品定位

## 7. 接口设计建议

新增一个独立接口，避免复用当前过于简单的 `/api/stream` 语义。

### 7.1 `POST /api/play-source`

请求：

```json
{
  "url": "https://www.bilibili.com/video/...",
  "format_id": "80"
}
```

响应：

```json
{
  "playable": true,
  "type": "progressive",
  "poster": "/api/thumb?url=...",
  "title": "视频标题",
  "duration": 1234,
  "src": "/api/stream?...",
  "audio_src": null,
  "manifest_src": null,
  "headers_forwarded": true,
  "reason": ""
}
```

当不支持时：

```json
{
  "playable": false,
  "type": "unsupported",
  "poster": "/api/thumb?url=...",
  "title": "视频标题",
  "duration": 1234,
  "src": null,
  "audio_src": null,
  "manifest_src": null,
  "headers_forwarded": false,
  "reason": "当前平台仅提供分离音视频直链，暂不支持原视频页内播放"
}
```

### 7.2 现有 `/api/stream`

保留，但角色调整为：

- 只负责媒体代理
- 不再承担“播放源判断”
- 后续可以扩展：
  - `/api/stream/video`
  - `/api/stream/audio`
  - `/api/stream/manifest`

## 8. 后端实现建议

## 8.1 新增播放源描述模型

建议在 `video_service.py` 中新增：

```python
@dataclass
class PlaySource:
    playable: bool
    type: str  # progressive | hls | dash | separate_av | unsupported
    video_format_id: str | None = None
    audio_format_id: str | None = None
    video_url: str | None = None
    audio_url: str | None = None
    manifest_url: str | None = None
    headers: dict[str, str] | None = None
    reason: str = ""
```

## 8.2 核心判断逻辑

后端在解析缓存中优先识别：

1. 是否存在带音频的 progressive 流
2. 是否存在 HLS manifest
3. 是否存在 DASH manifest
4. 是否只存在分离音视频直链

### 推荐判断优先级

1. `progressive`
2. `hls`
3. `dash`
4. `separate_av`
5. `unsupported`

### 原因

1. progressive 最稳，浏览器支持最好
2. HLS / DASH 有成熟播放器生态
3. separate_av 在没有 manifest 时浏览器直接播放成本高、兼容差

## 8.3 代理策略

后端继续负责：

1. 透传 `Referer`
2. 透传 yt-dlp 提供的 `http_headers`
3. 支持 `Range`
4. 屏蔽不必要的 `accept-encoding`
5. 统一返回浏览器可识别的 `Content-Type`

## 9. 前端实现建议

## 9.1 播放器选型建议

### 推荐方案

**P0：先保留现有 `VideoPlayer.vue`，仅支持 progressive**

理由：

1. 改动最小
2. 能最快验证“原视频播放”用户价值
3. 不会引入过多新依赖

### P1 升级方案

**把 `VideoPlayer.vue` 升级为 `UniversalPlayer.vue`，底层可接 ArtPlayer 或 xgplayer**

理由：

1. 更适合 HLS / DASH / 字幕 / 时间戳
2. UI 更完整
3. 便于后续产品化

## 9.2 组件改造建议

### `App.vue`

新增状态：

- `playSource`
- `isLoadingPlaySource`
- `playSourceError`

新增动作：

- `onPlayOriginal()`

### `VideoResult.vue`

新增按钮：

- `播放原视频`

按钮规则：

1. 解析成功后显示
2. 获取播放源时显示 loading
3. 获取失败后给出错误信息

### `VideoPlayer.vue`

P0 保持原生 `<video>` 即可，但建议补齐：

1. `@error` 事件上报
2. 显式 loading 态
3. poster
4. 播放失败提示区

## 10. 开发步骤建议

## 第一步：只做方案最小闭环

1. 后端新增 `POST /api/play-source`
2. 先只返回 `progressive` 或 `unsupported`
3. 前端新增 `播放原视频` 按钮
4. 只有当 `playable === true` 且 `type === progressive` 时才替换封面为播放器
5. 失败时保留封面和下载功能

## 第二步：增强播放覆盖率

1. 在后端识别 HLS / DASH
2. 前端升级播放器壳
3. 根据 `type` 选择不同播放适配器

## 第三步：接入总结与字幕能力

1. 字幕列表点击驱动播放器 seek
2. AI 总结中的时间戳与播放器联动
3. 统一播放器状态管理

## 11. 测试方案

## 11.1 自主测试

每次开发完成后，至少执行：

1. 后端单元测试
2. 前端组件测试
3. 构建测试
4. 真实链路回归

### 建议覆盖

#### 后端

1. progressive 源识别成功
2. unsupported 源返回明确 reason
3. `/api/stream` 继续支持 Range
4. 请求头透传正确

#### 前端

1. 点击 `播放原视频` 后才请求播放源
2. progressive 成功时封面替换成播放器
3. unsupported 时显示错误提示且不切播放器
4. 播放失败事件能反馈给用户

#### 回归链路

固定使用同一条测试视频：

`https://www.bilibili.com/video/BV1XVDfBLE3D`

验证：

1. 解析成功
2. 点击 `播放原视频`
3. 如果返回 progressive，则能在页内播放
4. 如果平台只返回分离流，则页面明确提示“暂不支持原视频页内播放”

---

## 12. 验收标准

满足以下条件即可视为 P0 完成：

1. 用户解析视频后能看到 `播放原视频` 按钮
2. 点击按钮后，系统不会影响原有下载能力
3. 对可直接播放的源，封面区域能替换成播放器并正常播放
4. 对不支持的源，系统给出明确中文提示，而不是黑屏或假播放
5. 每次功能修改后都完成自主测试并反馈结果

---

## 13. 推荐结论

如果要兼顾“尽快上线”和“后续可扩展”，推荐按下面顺序做：

1. **先做 P0**
   - 新增 `播放原视频`
   - 只支持 progressive
   - 不支持就明确降级

2. **再做 P1**
   - 升级播放器底层
   - 支持 HLS / DASH
   - 再接字幕和时间戳跳转

这样可以避免一开始就陷入“所有平台都要原视频页内播放”的高风险实现。

---

## 14. 需要人工确认的点

在进入开发前，建议用户先确认以下 3 点：

1. 是否接受 P0 只保证 `progressive` 原视频页内播放，遇到分离流时给出明确提示？
2. `播放原视频` 按钮是否采用“手动点击后再加载播放器”的交互？
3. P1 播放器升级时，更倾向于：
   - 继续用原生 `<video>` 逐步补强
   - 直接切到 `ArtPlayer`
   - 直接切到 `xgplayer`
